# Reply diagnostics

In chat, open **Settings → Reply diagnostics**. The panel refreshes on open and has a Refresh button. It shows the latest 20 requests in the open conversation, including stopped and failed attempts. Switching conversations changes the scope; old replies without measurements remain labeled as unavailable.

The active provider/model is read from current settings. Each measured request records the provider/model actually called, so a later provider switch doesn't relabel earlier work. Measurements are kept in the local SQLite reply ledger, included in backups, and removed with the associated request/conversation. No separate analytics service, tracking ID or telemetry export is used.

- **First text** starts when the background reply worker begins and ends at its first visible response event. **Total** includes context preparation, synchronous model/tool work and persistence until that worker finishes. These are wall-clock timings, not GPU timings or a browser/network benchmark. A restarted process cannot reconstruct an unfinished request's duration.
- **Reported tokens** come from the provider's response usage fields. Multiple synchronous calls/tool rounds are summed. Missing final usage stays unknown; when some calls report usage, the panel labels the sum as partial. Zero is shown only when explicitly reported.
- **Reported cost** currently supports OpenRouter's reported credit cost. It is never calculated from a price table, guessed from token counts or treated as zero when absent. OpenAI and custom servers may report token counts without a cost; that is displayed as Not reported.
- **Token estimates** use roughly 3.2 characters per token, with request JSON overhead for input and visible text for output. They can differ substantially from actual tokenization, particularly for code, non-English text, reasoning and images. They are not billing figures.
- **Context estimate** records the reply's system prompt and selected chat estimates, the context limit and its source (configuration, provider metadata or a fallback assumption), history selection, reserved reply room and the request's maximum output. Additional tool rounds can have larger prompts. The existing history selector reserves at most 20% of context for output; the requested maximum may be larger. A negative estimated remainder signals pressure, not a token-exact rejection prediction.
- **Notebook/compaction** reports whether notes are updating, failed update count, waiting user messages and the last compacted message. A correction/forget boundary and paused knowledge are shown separately. Compaction leaves visible chat intact. A requested compaction is shown with that reply; the current notebook state tells you what finished.

Coverage is deliberately limited to calls owned synchronously by a durable chat request, including a first-use tool capability probe. Background note writing, memory extraction, image generation, speech and independent legacy API calls are outside these totals. This panel is a debugging aid, not an account-wide invoice. Provider billing is authoritative.

The read-only endpoint is `GET /api/diagnostics?session_id=<id>` and has `Cache-Control: no-store`. It returns measurements, never prompts, message text, credentials, endpoint URLs or notebook text. Existing local/remote access policy applies.

Streaming usage follows the [OpenAI API's final usage chunk](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create) and [OpenRouter's usage accounting](https://github.com/OpenRouterTeam/docs/blob/main/cookbook/administration/usage-accounting.mdx). The app requests `include_usage` from the official OpenAI endpoint; local and custom servers retain their previous request shape for compatibility.
